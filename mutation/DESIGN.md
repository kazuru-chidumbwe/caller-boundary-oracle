# Mutation baseline: design (frozen 8 October 2026)

Frozen 8 October 2026, before any mutation code was written or run. Later changes are listed at the end with their date and reason.

RQ1: Does the caller-boundary oracle detect hidden failures that an "any error returned" check, output-differential testing and the ICAO system-level verdict miss?

## 1. Mutants

**Sites.** The M1 sites (`mining/m1-sites.csv`, 484 sites) whose `step_hint` is PACE, CA or AA: 349 sites (PACE 276, CA 47, AA 26). BAC and SM sites are left out because no suite injects a BAC failure, and an SM mutant changes every step at once.

**Operators.** Five failure-hiding operators. Each is applied only where the site kind allows it:

| Op | Name | Applies to kind | Change |
| --- | --- | --- | --- |
| O1 | drop raise | raise | remove the throw or error return; execution continues after the site |
| O2 | error to success | check | the failure branch returns the success value (nil error, success result) |
| O3 | swallow in catch | catch | the catch body is replaced by nothing (no rethrow, no status write) |
| O4 | skip status write | status_write | the assignment that records the failure is removed |
| O5 | invert check | check | the failure condition is negated |

Expected size: about 450 mutants. Each mutant is one source patch, generated by a script from the site list (file, line, kind) and reviewed by hand only for compile errors. Mutants that do not compile are dropped and counted.

**Libraries.** gmrtd (three pins), JMRTD 0.8.9 (built from the 0.8.9 sources jar), emrtd-dotnet, dmrtd. **Proposed: NFCPassportReader left out** (iOS Simulator on CI only, about 7 minutes per build; 64 sites would need about 80 CI runs). Stated as a threat. Decision D1 below.

## 2. Runs per mutant

Behaviour is uniform across failure kinds within an arm and step (see `analysis/out/RESULTS.md`), with two exceptions that depend on the status word. A reduced suite therefore keeps the cost down without losing those exceptions:

- PACE: at each harness fault point (MSE:Set AT, General Authenticate step 1) status words 6A80 and 6F00 and one channel fault (timeout); on the independent chip, 6A80 at General Authenticate step 3.
- CA and AA: 6300, 6700, 6A80, 6F00 (covers both status-word-dependent behaviours).
- Every arm of the library, plus the two controls and one positive control.

About 15 to 20 runs per mutant and arm. Mutants are only run on the cells of their own step; a CA mutant is not run on PACE cells.

The unmutated library runs the same reduced suite once (the reference observations). It must reproduce the verified outcomes of the full evaluation, or the mutation run stops.

## 3. The four oracles

All four read the same run artifacts, so the only difference between them is what each looks at.

| Oracle | Looks at | Verdict per run |
| --- | --- | --- |
| CBO (ours) | fired, failed, succeeded, returned_error, status_signal | the outcome of Algorithm 1 |
| Any error | returned_error | error / no error |
| Output differential | returned_error and the data the read returned (DG1 bytes, access control used) | accept with data D / reject |
| ICAO P4 verdict | returned_error or status_signal, without fired | failure indicated / not indicated |

**Kill.** A mutant is killed by an oracle if, on at least one run, that oracle's verdict differs from its verdict on the same run of the unmutated library.

**Output differential, defined.** In the literature this compares implementations with each other. Here it compares the mutant with the unmutated library on the same input, which is the most favourable setting for it (a perfect reference). Proposed as decision D3.

**ICAO P4 verdict, defined.** The conformity test passes when the inspection system indicates the failure to the operator. At library level we read "indicates" as any caller-visible signal (error or status field), and the test has no notion of whether the failure was delivered. Decision D4.

## 4. What is reported

- Table: mutants killed per oracle, by library and operator, out of the mutants that compiled.
- The main quantity: mutants killed only by CBO, and why (status-only versus silent; status writes removed; failure no longer delivered).
- Mutants killed by no oracle: inspected by hand for equivalence (does the site matter to any injected fault?) and reported as equivalent or not reached. Equivalent mutants hide from every oracle equally, so they do not change the comparison.

## 5. Threat to state up front

CBO observes everything the other three observe plus the status field and the delivery report, so on delivered runs it kills at least what they kill, by construction. RQ1 is therefore not a contest; it measures the size of the gap: how many failure-hiding mutants are invisible to accept/reject-level and error-level oracles. The one place a baseline can kill and CBO cannot is a run where the fault was not delivered (CBO says not applicable for both). Those cases are reported, not hidden.

## 6. Cost estimate

gmrtd: about 90 sites × 3 pins, Go build about 5 s, about 20 runs about 10 s: under 2 hours. JMRTD: about 115 sites, Maven build of the patched jar about 40 s: about 3 hours. dmrtd about 88 sites, emrtd-dotnet about 9: about 2 hours. Total about 7 to 8 hours on one Linux host.

## Decisions (accepted 8 Oct 2026)

- **D1** NFCPassportReader left out of the mutation study; stated as a threat.
- **D2** Reduced suite as in part 2.
- **D3** Output differential against the unmutated library (most favourable reference).
- **D4** ICAO P4 verdict read as "error or status field", no delivery check (most generous reading of the test text).
- **D5** SM sites excluded from the main table; reported in a small side table on the CA and AA cells.

## Changes after freezing

All recorded on 8 October 2026, before any mutant was generated or run.

1. **Site list.** The M1 list was corrected before mutants were generated (commit 9ad4950): sites whose step is named only in the lines around them, and sites in Chip Authentication sender classes, had been left out, and identical lines in different functions had been merged. The list grew from 484 to 526 sites; all earlier IDs are unchanged. Mutants are drawn from the corrected list.
2. **O2 as implemented.** Returning a typed success value cannot be written generically across five languages. O2 therefore makes the failure check never fire: an error test `c` becomes `false && (c)`, a success test `c` (comparison with a success status, `nil` error or 9000) becomes `true || (c)`. Execution then takes the path it would take had the step succeeded, which is the effect the operator is meant to model.
3. **Output for the output-differential oracle.** Every accepted read in this harness returns the same chip contents, so comparing data bytes adds nothing. The output is: rejected (error returned), or accepted together with the access control actually established (PACE or BAC).
4. **Runs that are not deterministic.** Runs against the independent chip use fresh keys and can fail for reasons unrelated to the mutant. A difference from the reference on such a run counts only if it repeats when that run is executed once more.
5. **Builds and runs that fail.** Mutants that do not compile are counted and reported, not scored. A run that crashes or exceeds 60 seconds is reported as a crash or timeout; mutants with such runs are reported separately and not counted as kills for any oracle.

Recorded on 8 October 2026 **after** the first scoring (`mutation/out/RESULTS.md`, harness `0c693a4`). Results under the frozen rules above are reported unchanged; the items below add analysis and are reported as exploratory, side by side with them.

6. **Reachability.** In the first scoring 524 of 684 compiled mutants were killed by no oracle, most of them at sites that no run executes. A probe per site (a statement that records that the line ran; all probes of one library version are built together in a separate copy of the source and the reduced suite runs once; refined 8 Oct before the probe ran) separates "not reached" from "reached but not killed". Scores are then also given over reached mutants.
7. **Kills by run type, per arm.** The frozen rule counts a kill on any run. Three kinds of run behave differently: runs where the injected failure was delivered in both the reference and the mutant (failure reporting can change), runs where delivery itself changed, and control runs with nothing injected (where a mutant can break an ordinary read). `mutation/breakdown.py` reports kills per kind and, on delivered runs, each change of outcome with the oracles that saw it.

8. **Unit of analysis: the arm.** An arm is one library build plus one caller choice, the unit in which behaviour is reported (paper, Section 3.4). Scoring whole mutants lets a guard arm, which turns a recorded failure into an error, give the error-based oracles visibility that a caller using the default arm does not have. `mutation/per_arm.py` scores (mutant, arm) pairs: a pair is a failure-reporting change when the caller-boundary outcome differs on a delivered run, and each oracle's detection of those pairs is compared with McNemar's exact test. Control-run breakage and delivery changes are reported in their own lines.
9. **Site list corrected again (Go).** The gmrtd decision that its 1.1.3 release changed (`if Session.PaceErr == nil`) and the reader lines that record PACE, BAC, Chip and Active Authentication failures in the session were not in the list: the Go check pattern matched only `!= nil`, and the failure-value test did not recognise fields named `...Err`. Both patterns were widened; the list grew from 526 to 534 sites, all earlier IDs unchanged. Mutants for the new sites are generated and run with the same runner, reference runs and reduced suite; mutants already run are unchanged.
10. **O4 implemented.** Part 1 lists O4 (skip status write) for status-write sites, but no PACE, CA or AA site outside NFCPassportReader had that kind until change 9. For Go, O4 replaces the error field among the assignment targets with the blank identifier, so the failure is not recorded and execution continues as before.
11. **Negative control from the probe builds.** Recorded after the probe ran. The probe builds add a statement at every probed site that only prints to the error stream, so each build is a set of neutral mutants. `mutation/noop_control.py` compares every probe run with the reference run of the same entry: no oracle may differ. Result: 188 runs, no difference for any oracle (`mutation/out/NOOP-CONTROL.txt`).
